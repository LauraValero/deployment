🏗️ PRE-DEPLOY

Preparar y validar antes de publicar

Técnicas 1, 2 y 3

1. CI/CD con validación IA

CI (Continuous Integration) = cada push ejecuta tests
CD (Continuous Deployment) = si pasa, se publica solo

¿Qué es?

Pipeline donde una IA revisa tu código, ejecuta tests, y bloquea el deploy si detecta bugs o vulnerabilidades. [1][4]

Ejemplo real

  • GitHub Copilot: 60M+ code reviews [9]
  • CodeRabbit: revisa PRs automáticamente
  • Esta presentación usa GitHub Actions
📊 Copilot detecta bugs en el 30% de PRs antes del merge [9]

CI/CD

Push → GitHub Actions valida → Vercel despliega en ~7s [1][9]

2. GitOps

¿Qué es?

El repositorio Git es la única fuente de verdad. La IA reconcilia automáticamente el estado del servidor con lo que dice el repo. [1][3]

Ejemplo real

  • ArgoCD / Flux
  • Vercel: cada push = deploy
  • Si alguien cambia algo a mano → la IA lo revierte
💡 Como tener un contrato escrito: si no está en el repo, no existe

GitOps — Repo = Producción

Cada commit en main se refleja automáticamente en el sitio live [1][3]

3. Infrastructure as Code con IA

¿Qué es?

Describes tu infraestructura en lenguaje natural → la IA genera Terraform, Docker, o configs listas para usar. [3][6]

Ejemplo real

  • Pulumi AI
  • Claude/Copilot generando Dockerfiles
  • El vercel.json de esta presentación
💡 Pedirle a un arquitecto que dibuje planos describiendo la casa con palabras

Infrastructure as Code

vercel.json + deploy.yml definen toda la infra — sin clicks manuales [3][6]

🚦 DEPLOY

Estrategias para entregar con mínimo riesgo

Técnicas 4, 5 y 6

4. Canary Deployments con IA

¿Qué es?

Se despliega al 5-10% del tráfico. La IA monitorea métricas y si algo va mal, revierte automáticamente. [1][10]

Ejemplo real

  • Netflix Kayenta [10]
  • Vercel Preview Deployments
  • Google Cloud Deploy
95% → versión actual ✓ 5% → versión nueva 🔍

Preview Deployment (Canary)

PR #1 → Vercel genera URL de preview → versión nueva sin tocar producción [1][10]

5. Blue-Green Deployments

¿Qué es?

Dos entornos idénticos. La IA prueba el nuevo (green) a fondo y cuando confirma que funciona, switchea todo el tráfico. [1]

Ejemplo real

  • AWS Elastic Beanstalk
  • Kubernetes con services [3]
  • Rollback instantáneo: volver a blue
🔵 Blue (actual) ⇄ 🟢 Green (nuevo)

6. Feature Flags + Progressive Delivery

¿Qué es?

El código nuevo ya está desplegado pero desactivado. La IA decide a quién activarle features sin redesplegar. [11]

Ejemplo real

  • LaunchDarkly / Split.io
  • Netflix, Spotify, Meta [10]
  • Activar feature solo al 1% → medir → escalar
💡 Desplegar sin desplegar: el código está ahí, solo se "prende" cuando la IA dice

👁️ POST-DEPLOY

Monitorear, detectar y corregir en producción

Técnicas 7, 8, 9 y 10

7. Observabilidad con IA (AIOps)

¿Qué es?

La IA analiza logs, métricas y traces en tiempo real. Detecta anomalías y distingue errores nuevos de los que ya existían. [1][12]

Ejemplo real

  • Datadog AI / New Relic AI
  • Splunk AIOps [12]
  • Reduce 5000 alertas/día → ~100 accionables
📊 AIOps reduce el ruido de alertas en un 95% [12]

8. Self-Healing Deployments

¿Qué es?

El sistema detecta fallo post-deploy, diagnostica la causa, y se arregla solo: rollback, restart, o hotfix automático. [1][3]

Ejemplo real

  • Kubernetes auto-restart [3]
  • AWS Auto Scaling
  • Un doctor robot 24/7
💡 Nadie se despierta a las 3am — el sistema se cura solo

9. Rollback Automático con IA

¿Qué es?

Motor de decisión que en segundos decide: ¿revertir o intentar arreglar? basándose en métricas, impacto en usuarios, y severidad. [1][5]

Ejemplo real

  • Vercel: rollback en 1 click
  • ArgoCD: auto-sync a versión anterior
  • Decisión en segundos, no minutos
💡 Como un capitán de bomberos que decide instantáneamente por dónde atacar el fuego

Rollback instantáneo

8 versiones disponibles en Vercel → revertir en <1 segundo [1][5]

10. Chaos Engineering con IA

¿Qué es?

La IA rompe cosas a propósito en producción para verificar que self-healing, rollback y alertas funcionen de verdad. [10]

Ejemplo real

  • Netflix Chaos Monkey [10]
  • Gremlin / Litmus
  • "¿Qué pasa si se cae un servidor?"
💡 Simulacro de incendio: verificar que el plan funciona antes de la emergencia real

Niveles de supervisión humana

HITL — Human-in-the-Loop

Nada se ejecuta sin validación humana explícita. [7][8]

Ej: code review antes de merge

HOTL — Human-on-the-Loop

La IA actúa, el humano supervisa y puede intervenir. [7]

Ej: deploy automático con alertas

HOOTL — Human-out-of-the-Loop

La IA actúa sin supervisión, regida por políticas. [8]

Ej: auto-restart de pods en K8s

¿Cuál usar?

No es categoría fija — es una trayectoria. Se empieza con HITL y se escala según confianza. [7][8]

✅ Buenas prácticas con IA en deployment

Humano + IA = equipo

  • Empezar siempre en HITL — escalar solo con confianza demostrada [7][8]
  • Siempre tener rollback antes de desplegar
  • Preview en cada PR — nunca directo a producción
  • Entender lo que la IA generó antes de hacer merge

Automatizar con criterio

  • Tests obligatorios antes de deploy [4]
  • Feature flags para cambios riesgosos [11]
  • Monitoreo post-deploy siempre activo [12]
  • Documentar la infra en código, no en wikis
📊 Equipos con code review + CI/CD tienen 4x menos incidentes en producción [9]

⚠️ Errores comunes (lo que NO hacer)

Confiar ciegamente en la IA

  • Saltar a HOOTL sin haber validado en HITL primero [7][8]
  • Copiar código generado sin entenderlo
  • "La IA lo hizo, no es mi responsabilidad"
  • No tener plan de rollback

Saltarse el proceso

  • Push directo a main sin PR ni review
  • Configurar servidores a mano (sin IaC)
  • Ignorar alertas post-deploy [12]
  • Desplegar viernes a las 5pm 😅
💡 La IA es un copiloto, no el piloto. Tú decides cuándo despegar y cuándo abortar.
